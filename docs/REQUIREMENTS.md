# NetLet requirements, against the code

Every requirement in *Netlet — Requirements Document (Developer Version)*
(version 11 August 2026), mapped to what is actually in this repository.

Status is deliberately harsh. **Built** means it works end to end against a
real database and a real server. **Partial** names the gap rather than
rounding up. Nothing is marked done because the schema could support it.

**These numbers are counted, not typed.** `scripts/check-requirements.mjs`

## 2. Architectural principles — 2 built, 1 partial, 1 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 2.1 | Fully microservices-based | **Not started** | One Express + tRPC app, one Postgres, one Vercel function. The seams are clean — each `server/` module has 1–4 relative imports and **no cross-module transactions** — so splitting later is packaging, not a rewrite. See the note at the foot of this file. |
| 2.2 | Easy for all five parties | **Built** | All five now have a real interface, and the fifth was the whole of this gap. The buyer has the storefront; the vendor and the admin share `/admin`, scoped by the server; the person who processes orders has `/admin/orders`, where a line is moved from pending to delivered and a driver's cash is recorded; and the delivery company has `/admin/dispatch` — see 3.4.1. What is still thin is named under 3.4 and is not a missing audience: there is no map and no live ETA. A courier can see every parcel assigned to them, what it takes to carry, where it goes and how much cash to collect, and can mark it collected and handed over. |
| 2.3 | Every advanced feature optional | **Built** | `/admin/features` is the switchboard — twelve switches, admin-only (`platform.configure`), every change on the audit trail with the authorisation chain. `shared/features.ts` is the list and is pure, imported by both sides, so the page hides exactly what the API refuses. **A switch closes the door; it never locks anybody in the room**: off refuses *starting* something — a message, a return, a price request, a claim, a gift card — and leaves everything already in motion to finish, so an open return is still refunded and an agreed price still honoured. The refusal is one middleware on the base procedure, by path, the shape `refuseNul` already has, so no router can forget it; a test fails if a switch names a procedure the API does not have. Rails answer empty rather than refuse. **`ai` is the one switch over every model call** — assistant, search refinement, recommendation ordering, the review queue's model pass — each landing on the deterministic fallback it already had for "no key". Absent is on: a database nobody has touched behaves exactly as before. What is still per-vendor rather than per-shop is unchanged and already existed: `autoPublish`, cash on delivery, accepting price requests. |
| 2.4 | AI core, not an afterthought | **Partial** | AI now runs through the shopper's side and the operator's: the recommendation rail and its model reorder pass (3.1.5), search refinement, the product assistant on every product page, auto-categorisation on bulk upload (3.3.5), the review queue's triage with a model pass that can only add a concern (3.3.6), and fraud signals on orders (3.6.5). Every one carries the same guardrails — a model reorders or flags but never chooses or refuses, no shopper's identity leaves NetLet, merchant text is fenced as data, and every failure lands on a deterministic answer — and one switch (`ai`, 2.3) turns every model call off at once. Still absent, and why this stays partial: the AI contact centre (3.5.1), imaging (3.3.4, 3.1.10, 3.1.8), visual search (3.1.6, drawn not wired) and the language-model half of anything a shopper asks a person today. The size guide (3.1.20) learns from returns instead. Several of those wait on providers rather than code. |

Points are a discount and not a deposit, so a spend is capped at the order. ## 3.2 Checkout & payments — 8 built, 1 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 1 | KNET, cards, Deema BNPL, payment link | **Not started — set aside** | No provider touched, by instruction. Everything below waits on it. |
| 2 | COD by default, disableable | **Built** | Cash on delivery is **not a payment integration**, which is why it lands while 3.2.1 does not: nothing is authorised, captured or settled. `shared/commerce/payment.ts` is the rule and is pure. On by default — a seller opts *out* — so a new store that has recorded nothing is still buyable from, and a seller may set the most they will send a driver to collect. **A basket is one payment, so one refusing seller refuses the basket**: quietly dropping them would be editing somebody's basket to make a button work. Availability is decided server-side and checked again at order time, because a seller may turn cash off between the page rendering and the button. **This is the first thing in NetLet that places a real order.** It is written `pending_payment` and stays there until a seller records the driver collected — marking it paid at checkout would put revenue in the finance panel that nobody has. Nothing is a stored state: expired is `ends_at` having passed and used up is a count of redemption rows, so nothing has to run, and the rows cannot double-count the way a column two orders race would. A card's balance is taken with the predicate inside the write — `remaining = remaining - n WHERE remaining >= n`, the stock take's own shape — and handed back when the order fails, beside the stock and the points. Everything is frozen on the order. **A discount code is NetLet's own promotion**: a seller's would reduce their takings and change the commission split on their lines, which is a decision about money rather than a default to pick, so it is deliberately absent and `vendor_id` is not invented for it. Verified in a browser in both languages, axe clean: minted, typed, refused when unknown, applied, and spent down to a real balance on a real order. |
| 4 | Multi-vendor cart, delivery cost per vendor | **Built** | The cart was already multi-vendor and `sliceByVendor` already grouped an order that way; what was missing was the money. `shared/commerce/delivery.ts` is the arithmetic and is pure. Each seller charges their own fee and the shopper pays each — a basket from three shops is three parcels, and one averaged figure charges the cheap seller's customers for the expensive one. **Free-over is measured per seller, never across the basket**, or one seller's money pays for another's sale, and **the shortfall is shown** because a threshold nobody can see is just a higher price with a rumour attached. A seller who recorded no fee delivers free, which errs toward the shopper. The order **computes the total rather than taking it from the caller** — it used to be a parameter on the honest grounds that there was no rate card, and leaving it one now would let whoever posts the order set their own postage — and freezes the per-seller breakdown beside it, so an old order still says who charged what. | 5 | Delivery speed per product | **Built** | A band the seller picks — same day, next day, 2–4 days, within a week, made to order — resolved product-over-store in the shape the commission rate already uses, so "no opinion about this one" stays a different instruction from choosing the slowest band. `shared/commerce/deliverySpeed.ts` is the rule and is pure. **The Kuwaiti weekend is Friday and Saturday**, and the arrival dates are counted in business days across it: plain calendar arithmetic would promise a Thursday order on a Saturday, which nobody here can keep. A same-day order placed on a Friday goes out on Sunday for the same reason. It is **the seller's statement and the line says so** — NetLet has no carrier integration, so anything calling itself an ETA would be invented — and nothing is drawn when nothing was stated, because a default band would be NetLet promising on a seller's behalf. Made to order has no window at all rather than a guessed one. A pre-ordered line shows none of it: the release date is the promise there, and two answers about one parcel is how a shopper believes the wrong one. One component draws it on the product page and in Quick View, so they cannot disagree. |

## 3.3 Vendor experience — 20 built, 1 partial, 1 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|

| 6 | E-invoice compliance | **Partial** | The mechanics are built; whether they satisfy the law has not been checked by anybody qualified to say, and that is the gap. `shared/commerce/invoice.ts` is the rules and is pure; `invoices` and `invoice_counters` are the ledger. **One invoice per order, issued by NetLet** as the marketplace the shopper paid, with every seller named under their own heading and their own commercial registration — or "sells under NetLet's licence" in words — because the order-level reductions belong to the basket and splitting them per seller would need an allocation rule nobody has decided. **Issued when the cash is collected**, from the frozen order, so a line cancelled before then is no more on the invoice than on the driver's sheet. **Gap-free numbering** (`INV-2026-000042`), from a counter row incremented inside the transaction that writes the invoice — a Postgres sequence would leave a hole every time an insert failed. **Never edited**: the whole document is frozen as issued, and a refund adds a credit note (`CRN-…`) against it. Both languages on one document whatever the site is in, the date in the Gregorian and Hijri (Umm al-Qura) calendars, amounts in KWD to three decimals, and an invoiced order cannot be deleted out from under its invoice. The shopper finds it on their order; an administrator at `/admin/invoices`. **Every document can be checked by whoever holds the paper**: a random code is issued with it and printed beside a QR that opens a public page confirming the number, date, total, issuer and sellers — never the buyer — and saying if a credit note has corrected it; a wrong code and an unknown number get the same answer. Each document also downloads as structured data (JSON) for an accountant's software. The field list followed secondary summaries of Kuwait's Decree 10/2026 rather than the decree itself, NetLet's own registration has to be configured (`INVOICE_ISSUER_*`; `pnpm preflight` warns), and there is no submission to any government system because no such interface was specified. |

## Repository structure

Two fixes, both measured rather than felt:

  `client/src/hooks/`. Moved.

Still outstanding: **`server/inventory.ts` is 1957 lines** (1388 when this was first written — it has grown, which is the argument) and wants splitting
on the section banners it already has. It has shared module-local internals,
so it is worth doing while landing a feature that touches it — then the
feature's own tests prove the seams — rather than as a move on its own.

## The one recommendation I would put in front of the plan

**Stay a modular monolith until payments and fulfilment are real, then split.**

The goal in 2.1 is that a new feature ships without disturbing the rest of the
system. That goal is met today by the module boundaries, not by the network:
`shared/` is pure and holds every rule that costs money or access, guards sit
next to the queries they protect, and no transaction spans two modules. Those
are the properties that make a split cheap — and they are exactly the
properties a premature split destroys, because once `orders` and `inventory`
are two services, taking stock during checkout stops being a transaction and
becomes a saga with compensating writes.

The cost of waiting is low: the seams are measured above and they hold. The
cost of splitting now is paid on every feature in this document, before a
single dinar has been taken.

If the answer is still "split now", say so and I will — the document wins over
my recommendation. But I would want the payment and delivery services carved
out **first**, since those are the two with genuinely independent failure
modes and genuinely different scaling, and the rest to follow only when
something forces it.

# NetLet requirements, against the code

Every requirement in *Netlet — Requirements Document (Developer Version)*
(version 11 August 2026), mapped to what is actually in this repository.

Status is deliberately harsh. **Built** means it works end to end against a
real database and a real server. **Partial** names the gap rather than
rounding up. Nothing is marked done because the schema could support it.

| | count |
|---|---|
| Built | 42 |
| Partial | 8 |
| Designed, not wired | 1 |
| Not applicable | 1 |
| Not started | 25 |

*Last updated after landing fraud signals on the order desk (3.6.5). Card payments and
everything gated on them are deliberately untouched — see the note under 3.2.*

**These numbers are counted, not typed.** `scripts/check-requirements.mjs`
derives them from the rows and `scripts/requirements.test.ts` fails the build
when the written totals disagree — because the first version of this table was
hand-maintained and was wrong: it claimed 12 built and 12 partial when the rows
said 11 and 11, an off-by-one in each direction that cancelled out in the grand
total and so looked correct. A status table that misreports its own status is
worse than no table, for the reason `QueryGate` exists: it reads as working.

## 2. Architectural principles

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 2.1 | Fully microservices-based | **Not started** | One Express + tRPC app, one Postgres, one Vercel function. The seams are clean — each `server/` module has 1–4 relative imports and **no cross-module transactions** — so splitting later is packaging, not a rewrite. See the note at the foot of this file. |
| 2.2 | Easy for all five parties | **Partial** | Buyer, vendor and admin each have a real interface, and the person who processes orders now has one too: `/admin/orders` is the desk where a line is moved from pending to delivered and a driver's cash is recorded. **The delivery company still has no interface at all** — one of the five audiences is absent, not merely rough. |
| 2.3 | Every advanced feature optional | **Partial** | The habit exists: `autoPublish` per vendor, Firebase-or-scrypt chosen by config, `SEARCH_MODES_WIRED`, and nothing throws at boot so a missing value is a dead feature rather than an outage. There is no feature-flag system as such, and no per-vendor or per-tenant switchboard. |
| 2.4 | AI core, not an afterthought | **Partial** | Two real uses: the recommendation rail (`server/recommendations.ts`) and `search.refine`. Both carry the guardrails worth keeping — a model reorders but never chooses, only interest terms leave NetLet, every failure falls back to a deterministic answer. Customer service, product management, imaging and fraud are all absent. |

## 3.1 Customer experience — 16 built, 0 partial, 1 drawn, 4 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 1 | Back-in-stock request, vendor sees demand | **Built** | `followed_products`; `customer.follows.demand` is public so the "N people are waiting" line can render. Vendor-side surfacing needs a panel. |
| 2 | Optional installation fees, extended warranty | **Built** | `shared/commerce/addons.ts` is the arithmetic and is pure. **Charged per unit**, because two fridges need two fittings and charging per line makes somebody buying three pay for one and argue about it on the doorstep. **The money goes into the line it belongs to**, so `line_total` still covers everything the line is worth and `commission + vendorNet === lineTotal` still holds exactly — the identity the finance panel is tested against — rather than a separate pot with its own rate, its own report and its own refund rule describing the same transaction. **Nothing is ticked by default, ever**: a pre-ticked warranty is how a shopper pays for what they did not ask for and did not notice, which is the one thing this feature could do that would be worse than not having it. The cart stores *which* extras and never what they cost, exactly as it stores no prices; the order freezes the label and the figure beside the price, so a seller changing an extra afterwards cannot rewrite what was charged. A free extra is refused where a seller records it — that is a feature of the product, and a check box that changes no figure is the dead-control rule. The seller's order desk lists what was bought with each line, because the seller is who turns up to fit the thing. Verified in a browser in both languages, axe clean: declared on the product, ticked by the shopper, carried through the bag and frozen on a real order. |
| 3 | Pre-order | **Built** | A pre-order is not an exemption from `stock >= n`; it is a second pool carrying the same predicate. `product_variants.preorder_stock` is what the vendor will promise ahead of arrival, taken with `preorder_stock = preorder_stock - n WHERE preorder_stock >= n`, so a vendor who promises 50 sells 50 and the fifty-first is refused by the same race-safe mechanism. The allowance is also the flag — two columns that must agree eventually do not. A line is wholly stocked or wholly pre-ordered, never split. `shared/commerce/preorder.ts` is the rule and is pure; the order line freezes whether it was a pre-order and the date promised, beside the price and the commission rate. |
| 4 | Public/private wishlists, found by phone | **Built** | `wishlists`, `wishlist_items`, phone key, claim holds, lookup throttle. |
| 5 | AI personalised recommendations | **Built** | `shared/commerce/taste.ts` + model reorder pass. |
| 6 | AI visual search (photo or description) | **Drawn, not wired** | `SearchModes.tsx` has every state designed. `SEARCH_MODES_WIRED` governs one line of copy; nothing is listening. |
| 7 | Variants: colour swaps photo, zoom, per-category attributes | **Built** | Swatches and zoom were already built; the missing half was the attribute schema. `shared/commerce/attributeSchema.ts` gives each department the rows a shopper actually compares on, **in code beside the departments themselves** — a table and an editor for it would be a second product to maintain before anybody asked for one. **The schema offers rows, it never restricts them**: anything a seller typed that it does not know about is kept, listed and untouched, because a schema that deletes merchant data on first save is one nobody uses twice. **The key is stable and the label is translated** — `ram` is what a facet groups on, "Memory" and "الذاكرة" are what people read — which is the fix for the same fact arriving as "RAM", "Ram Size" and "Memory (GB)" from three sellers. **The unit belongs to the field**, so one seller typing "16 GB" and another "16" cannot split a facet in two. A blank clears a row rather than storing an empty string, which would render as a label with nothing after it. |
| 8 | AI virtual try-on | Not started | |
| 9 | Product videos | **Built** | One ordered gallery with a `kind` column, not a second table: a video belongs *between* the photographs, and two ordered lists would force an interleave rule with no right answer. `Product.media` is the gallery and `Product.images` is the same list with the video removed — so every card, rail and thumbnail reads `images` and cannot render a video frame by construction. The player is the browser's own (`controls`, no autoplay, `preload="metadata"`), and the poster is optional because refusing the video over its garnish would be refusing the feature. |
| 10 | AI pulls manufacturer images | Not started | There is no image pipeline at all — vendors type URLs. |
| 11 | Quick View with quantity | **Built** | On every page that draws a card. |
| 12 | Category icons | **Built** | The icon lives on the department in `shared/commerce/departments.ts` as a name of what it depicts, and one client component turns that into a drawing — so the four surfaces that list a department cannot disagree. The home page *had* icons, chosen by array index through a nested ternary: Style drew `ArrowDownRight`, the same glyph used below it as the browse chevron, and every merchant department past the sixth drew a shopping bag. A department NetLet does not know gets a label tag rather than a guess. |
| 13 | Request a special discount (vendor opt-in) | **Built** | A shopper names a price, the seller answers, and the agreed figure applies to that shopper's bag and nobody else's. `shared/commerce/priceOffers.ts` is the rule set and is pure. Four stored states and two derived — expired from the date, used from the order — so nothing has to run for the row to stop meaning what it did. **The agreed price is a ceiling, never a floor**: if the shelf falls below it the shopper pays the shelf, because charging somebody more for having asked would be the worst thing this could do. **The cart still stores no price** — a grant is a fact about a shopper and a variant, so `cart_items` is untouched and the lookup happens where the price is resolved. It is deliberately *not* the offer machinery: no `compareAtPrice`, no strikethrough, no `−27%` badge, because those are an advertised saving and need a Ministry permit, while this is a private answer to one person. Opt-in per vendor with a per-product override in both directions, the same three-state shape the commission rate uses. One open request per shopper per variant, enforced by a partial unique index rather than a check two tabs can race. Throttled in Postgres by account — the one ceiling keyed that way, because what runs out is a seller's patience. Verified end to end in a browser against real Postgres: asked, answered, applied in the bag, spent by the order, and refused on the second try. |
| 14 | Referral, two tracks | **Built** | A code on every account, derived from its id rather than stored — one account has one code for ever and there is no second copy to edit into a collision — using the alphabet the order reference uses, since a code is read out loud far more often than an order number. `shared/commerce/referral.ts` is the arithmetic and is pure. **Both tracks are paid, and both at the same moment**: the friend's first order being *paid for*, not their registration. A scheme that pays at sign-up pays for sign-ups, and a cash order nobody collects has earned nobody anything — so the hook is `recordCashCollected`, where the money actually arrives. Exactly-once twice over: a unique index on the referred account, so two tabs cannot both claim it, and a partial unique index on (referral, reason) behind a `qualified_at is null` predicate. Self-referral is refused, which is the whole of the fraud model enforceable without identity NetLet does not have; claiming more would be theatre. The code survives the walk from the invitation link to the registration form in `localStorage`, and is forgotten once used. **The account page says how many arrived and never who** — a code is meant to be pasted into a group chat, and a list of names would make it a way of asking which strangers have registered. Verified end to end in a browser against real Postgres: arrived on `?ref=`, browsed away, registered, bought, collected, and both balances moved. |
| 15 | Referral points, spend or cash out at 10% | **Built** | **A balance is never stored** — it is the sum of `point_entries`, always, because a stored total beside its own evidence disagrees with it the first time a write fails halfway, and the shop's answer is then the one nobody can audit. Every row carries why it exists. Points spend at face value inside NetLet and cash out at a tenth, which is not small print: what is spent here comes back as a sale and what is paid out does not. **Spending comes out of NetLet's cut and never the seller's** — no line moves, `vendor_net` is what it would have been, because a marketing scheme funded out of somebody else's revenue is one they never agreed to. Taken the way stock is taken: before the write, handed back if it fails, and refused rather than overdrawn — the balance check is inside a transaction that locks the account row, since a ledger has no single row for a predicate to guard. Points are a discount and not a deposit, so a spend is capped at the order. Cashing out writes the entry immediately (the balance has to fall or the same points go in another tab) and `settled_at` records the transfer, listed for an admin beside the seller payouts — the same shape, because NetLet has no rail that pays anybody automatically. Verified in a browser in both languages, axe clean: spent at checkout, cashed out, settled. |
| 16 | Reviews: verified purchase, after delivery | **Built** | `reviews`, keyed on an **order line** — so "verified" is structural rather than a flag, and one purchase buys one review. Gated on `order_items.delivered_at`, a column that now exists. Product page shows the average, a histogram and every review; `/account` lists each delivered line with a form or the reason there is none. Vendors reply, admins hide (never delete). Verified end to end in a browser against a real paid, delivered order. |
| 17 | Cart recovery reminder | **Built** | `shared/commerce/cartRecovery.ts` is the rule and is pure, and the interesting decision is not the arithmetic — it is being honest about what NetLet can do. **There is no mail provider and no scheduler**: Firebase sends the auth emails and nothing else, and nothing here runs on a timer. A recovery *email* needs both, and a reminder that depends on a cron nobody runs is a dead feature that looks finished. So it is **resolved on the read**, the way the discount permit and the pre-order date are: the moment a shopper with a stale basket opens their bag, the shop says so. Nothing has to run, it cannot go stale, and it reaches exactly the person it is about — and when a mail provider exists, this same function decides who gets the email. Quiet, and bounded at both ends: under `ABANDON_AFTER_HOURS` they are still shopping and a banner is nagging; past `STALE_AFTER_DAYS` the basket has been re-priced enough that "you left these" is a worse message than silence. It carries a count and an age and **never a total**, because a cart stores no prices and quoting a figure that has since moved is the shop arguing with its own page. |
| 18 | Price-drop alerts | **Built** | Same follow mechanism. |
| 19 | Subscribe & Save | Not started | |
| 20 | AI size guide | Not started | |
| 21 | Frequently bought together, cross-vendor | **Built** | `shared/commerce/together.ts`, scored on **lift** rather than raw co-occurrence — a bestseller shares baskets with everything, so counting pairs surfaces bestsellers and not complements. Reads orders *and* carts (3:1), so the rail works today rather than waiting on payments. Cross-vendor complements are kept and labelled "Another seller", which is where the value is. Draws nothing below `MIN_SUPPORT` baskets or `MIN_LIFT`, because the heading is a claim. |

## 3.2 Checkout & payments — 4 built, 2 partial, 3 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 1 | KNET, cards, Deema BNPL, payment link | **Not started — set aside** | No provider touched, by instruction. Everything below waits on it. |
| 2 | COD by default, disableable | **Built** | Cash on delivery is **not a payment integration**, which is why it lands while 3.2.1 does not: nothing is authorised, captured or settled. `shared/commerce/payment.ts` is the rule and is pure. On by default — a seller opts *out* — so a new store that has recorded nothing is still buyable from, and a seller may set the most they will send a driver to collect. **A basket is one payment, so one refusing seller refuses the basket**: quietly dropping them would be editing somebody's basket to make a button work. Availability is decided server-side and checked again at order time, because a seller may turn cash off between the page rendering and the button. **This is the first thing in NetLet that places a real order.** It is written `pending_payment` and stays there until a seller records the driver collected — marking it paid at checkout would put revenue in the finance panel that nobody has. The collection predicate is inside the `UPDATE`, so two people pressing it cannot both be told they recorded it — and it is **recordable**, from the seller's own order desk, which is what makes the second half of this real rather than a function nobody could call. |
| 3 | Points, gift card, discount codes | **Built** | All three at one field. Points are the ledger under 3.1.15; `shared/commerce/vouchers.ts` is the other two and is pure. **A code is a discount and a gift card is money**, and that sentence decides the order they apply in: the code comes off the goods, points come off next, and the card pays what is still owed — spending it first would use a customer's own money on a reduction the shop was giving away anyway. `settle` is the one place that order lives, so the checkout summary and the order writer cannot disagree. **One field for both**, because somebody holding a code does not necessarily know which kind it is, and the refusal names one fixable thing — not started, expired, all used up, already used by you, below the minimum — rather than the shrug that makes people type it four more times. Nothing is a stored state: expired is `ends_at` having passed and used up is a count of redemption rows, so nothing has to run, and the rows cannot double-count the way a column two orders race would. A card's balance is taken with the predicate inside the write — `remaining = remaining - n WHERE remaining >= n`, the stock take's own shape — and handed back when the order fails, beside the stock and the points. Everything is frozen on the order. **A discount code is NetLet's own promotion**: a seller's would reduce their takings and change the commission split on their lines, which is a decision about money rather than a default to pick, so it is deliberately absent and `vendor_id` is not invented for it. Verified in a browser in both languages, axe clean: minted, typed, refused when unknown, applied, and spent down to a real balance on a real order. |
| 4 | Multi-vendor cart, delivery cost per vendor | **Built** | The cart was already multi-vendor and `sliceByVendor` already grouped an order that way; what was missing was the money. `shared/commerce/delivery.ts` is the arithmetic and is pure. Each seller charges their own fee and the shopper pays each — a basket from three shops is three parcels, and one averaged figure charges the cheap seller's customers for the expensive one. **Free-over is measured per seller, never across the basket**, or one seller's money pays for another's sale, and **the shortfall is shown** because a threshold nobody can see is just a higher price with a rumour attached. A seller who recorded no fee delivers free, which errs toward the shopper. The order **computes the total rather than taking it from the caller** — it used to be a parameter on the honest grounds that there was no rate card, and leaving it one now would let whoever posts the order set their own postage — and freezes the per-seller breakdown beside it, so an old order still says who charged what. The bag and the checkout summary read Subtotal / Delivery / Total, with a line per seller that charges. |
| 5 | Delivery speed per product | **Built** | A band the seller picks — same day, next day, 2–4 days, within a week, made to order — resolved product-over-store in the shape the commission rate already uses, so "no opinion about this one" stays a different instruction from choosing the slowest band. `shared/commerce/deliverySpeed.ts` is the rule and is pure. **The Kuwaiti weekend is Friday and Saturday**, and the arrival dates are counted in business days across it: plain calendar arithmetic would promise a Thursday order on a Saturday, which nobody here can keep. A same-day order placed on a Friday goes out on Sunday for the same reason. It is **the seller's statement and the line says so** — NetLet has no carrier integration, so anything calling itself an ETA would be invented — and nothing is drawn when nothing was stated, because a default band would be NetLet promising on a seller's behalf. Made to order has no window at all rather than a guessed one. A pre-ordered line shows none of it: the release date is the promise there, and two answers about one parcel is how a shopper believes the wrong one. One component draws it on the product page and in Quick View, so they cannot disagree. |
| 6 | Different address per product | Not started | |
| 7 | Map address picker | Not started | Governorate select only. |
| 8 | Split an order into per-product operations | **Partial** | Fulfilment lives on the *line*, not the order, which is the hard half, and it is now **operable**: `/admin/orders` puts a control on every line and none on the order, because an order spanning three sellers can be fully paid while two have shipped nothing. `setLineFulfilment` had been written since the tables landed with no caller at all, so `delivered_at` had no writer — every line said "delivered" with a null date and nothing downstream ever opened. It is stamped when a line is marked delivered and cleared when it is moved back off, which is the uncomfortable half and still right: a seller correcting a mis-click has said the parcel is not there, and leaving the date would hold a return window open on it. Return and re-pickup as operations are still absent. |
| 9 | Fast checkout | **Partial** | The page exists; there is nothing to pay with. |

## 3.3 Vendor experience — 17 built, 2 partial, 3 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 1 | Self-registration: account → choose vendor → documents → contract → approval | **Built** | `/sell`, on the storefront rather than in the portal, because the person filling it in has no portal to reach yet — and it is what the footer's "Sell with us" now points at, a link that had no destination at all. `shared/inventory/sellerApplication.ts` is the rule set and is pure. **Saving is easy and approving is strict**: a save refuses only what is actively wrong — a name it cannot exist without, an IBAN that fails mod-97 and would send money to an account that is not there, a document link that is not https — while everything merely absent is listed on the page, because refusing a save over a licence nobody has scanned is how a form goes unfinished. **Approving is the guarded step**, since approving is what creates the store, and both sides run the same `readyToApprove`, so the button cannot offer what the API refuses. **One approval, not two**: the vendor is written `approved` and the applicant attached as its owner in the same call, because a store left `pending` afterwards is a state somebody forgets and a seller who was told they were open and is not. A failure to attach the owner deletes the store again — a shop nobody can sign into looks finished, so nobody goes back to fix it. **One open application per account**, by partial unique index rather than a read-then-insert two tabs beat; approved and rejected rows fall out of it, so a rejection can be corrected and sent again and a second store can be applied for. The agreement is recorded **with its version**, because "they accepted the terms" means nothing without "which terms". Documents are links, not uploads, and the page says so rather than leaving somebody to find out — NetLet has no upload pipeline, which is the same reason a vendor types an image URL. A seller trading under NetLet's own licence is never asked for a number they do not have. Verified end to end in a browser in both languages, axe clean: applied, refused on a bad IBAN, completed, submitted, approved, and the new owner reached the portal and their store's Selling section. |
| 2 | Default commission shown at onboarding, propose custom | **Partial** | Commission is fully modelled; there is no onboarding to show it in. |
| 3 | Bulk upload by Excel, AI-assisted entry | **Built** | `/admin/import`. `shared/inventory/bulkUpload.ts` is the reader and is pure — the file is parsed in the browser by the same function the server would have used, so a 400-row preview is one round trip rather than an upload endpoint and a second call. **CSV rather than `.xlsx`**: Excel writes CSV from Save As, and parsing the other means a zip reader, an XML parser and a dependency carrying both to arrive at the same rows; the page says so rather than leaving somebody to find out from an error. Three things about real exports are handled because they are what actually breaks an importer — Excel's UTF-8 BOM, which makes an exact match on `title` fail on every file a Windows seller sends; quoted fields carrying commas and newlines; and the CRLF that turns a price into `"12.000\r"` and then into NaN. **The preview is the feature**: every problem is reported against its own line number and nothing is written until the seller presses the button, because an importer that writes on upload is one they have to undo a row at a time. All of it or none of it, in one transaction — a half-finished import cannot be told apart from a finished one, and re-running the corrected file duplicates whatever landed. Everything arrives as a **draft**, because publishing has its own rules and an importer that can put four hundred rows in the shop can put four hundred mistakes there. Handles are allocated up front and remembered, since `uniqueHandle` reads what is committed and two rows with one title would otherwise collide at the very end. Verified in a browser in both languages against real Postgres, with a file carrying a BOM, CRLF, a quoted comma and Arabic titles. |
| 4 | AI fixes images after upload | Not started | No upload exists. |
| 5 | AI auto-categorises on bulk upload | **Built** | `suggestDepartment`, scoring a title and description against each department's own words **in both languages** — an importer that only reads English auto-categorises half a Kuwaiti shop. **It never overrides a seller**: the guess is consulted only for a row that left the column blank, every guessed row is marked as guessed in the preview, and the count is stated so somebody who disagrees can fix the column and upload again. **Null is a real answer** — a product filed under the wrong department is harder to find than one filed under none, and a department this shop does not carry is never guessed into. Deterministic rather than a model call, which is the choice rather than a shortcut: this codebase's own rule is that a model reorders and never chooses, so the most one could honestly do here is pick among the departments already scored — for an answer a word match gets right on "Brass Reading Lamp", at the cost of a key, a network call and a timeout on the one path where being slow is most obvious. |
| 6 | AI reviews products, alerts admin | **Built** | `shared/inventory/productReview.ts` is the triage and is pure. **It flags and never refuses**: `assertPriced` and the discount permit are the two doors onto the shelf and they refuse on their own, so a third gate built on heuristics would mean a seller's listing rejected by a word list. Every finding is a reason to look, carried **with the evidence that produced it** — "there is a phone number in the title" shows which number — as message keys rather than sentences, because the queue is read in Arabic too. The checks are the ones that matter on a marketplace: contact details that take the buyer off the platform, a medical or money claim the shop cannot stand behind, a variant at zero (the refusal `assertPriced` will make anyway, surfaced so nobody presses approve and reads an error), no pictures, no department, a description that is not one, and a title in capitals — measured on the letters, so "SONY 4K" is a brand and a spec while "BEST DEAL EVER BUY NOW" is not. Serious first, because the ordering is the only prioritising this does. The model pass on top **can only add a finding**: it is asked for a concern and never a verdict, "approve" is not a word it may say, the listing is fenced and labelled data the way the shopper assistant's brief is, and every failure — no key, a timeout, a refusal, malformed JSON — leaves the deterministic flags unchanged. It is a press rather than automatic, since a queue of twenty would otherwise spend twenty calls on a scroll, and **with no key the button is absent** rather than answering "nothing found" about a question nobody asked. Verified in a browser in both languages against a real bad listing, axe clean; the model branch is exercised only in its absent state, because no key is configured here. |

## Repository structure

Two fixes, both measured rather than felt:

  which breaks this repo's own rule that every hook lives in
  `client/src/hooks/`. Moved.

Still outstanding: **`server/inventory.ts` is 1388 lines** and wants splitting
on the section banners it already has. It has shared module-local internals,
so it is worth doing while landing a feature that touches it — then the
feature's own tests prove the seams — rather than as a move on its own.

## The one recommendation I would put in front of the plan

**Stay a modular monolith until payments and fulfilment are real, then split.**

The goal in 2.1 is that a new feature ships without disturbing the rest of the
system. That goal is met today by the module boundaries, not by the network:
`shared/` is pure and holds every rule that costs money or access, guards sit
next to the queries they protect, and no transaction spans two modules. Those
are the properties that make a split cheap — and they are exactly the
properties a premature split destroys, because once `orders` and `inventory`
are two services, taking stock during checkout stops being a transaction and
becomes a saga with compensating writes.

The cost of waiting is low: the seams are measured above and they hold. The
cost of splitting now is paid on every feature in this document, before a
single dinar has been taken.

If the answer is still "split now", say so and I will — the document wins over
my recommendation. But I would want the payment and delivery services carved
out **first**, since those are the two with genuinely independent failure
modes and genuinely different scaling, and the rest to follow only when
something forces it.

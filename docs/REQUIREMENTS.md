# NetLet requirements, against the code

Every requirement in *Netlet — Requirements Document (Developer Version)*
(version 11 August 2026, [`Netlet-Requirements.pdf`](Netlet-Requirements.pdf),
the owner's own document), mapped to what is actually in this repository.

Status is deliberately harsh. **Built** means it works end to end against a
real database and a real server. **Partial** names the gap rather than
rounding up. Nothing is marked done because the schema could support it.

*Last updated after every row was checked again against the document's own
wording — [`Netlet-Requirements.pdf`](Netlet-Requirements.pdf), now in this
repository — rather than against the short titles this file had given its rows.
Eighteen rows that read built were partial against what the document actually
asks, and each now begins with **Against the document:** saying what is missing;
six rows that stay built carry the same note where the document asks for more
than was done. Two claims this file made were false and are corrected: that
administrator sign-ins reach the audit trail (3.6.3), and that voice and photo
search ship switched off (3.1.6). The heaviest finding is money: points cash
out at a tenth of their value where the document deducts a 10% fee (3.1.15).
Card payments and everything gated on them are deliberately untouched — see the
note under 3.2.*

**These numbers are counted, not typed.** `Backend/scripts/check-requirements.mjs`
derives them from the rows and `Backend/scripts/requirements.test.ts` fails the build
when the written totals disagree — because the first version of this table was
hand-maintained and was wrong: it claimed 12 built and 12 partial when the rows
said 11 and 11, an off-by-one in each direction that cancelled out in the grand
total and so looked correct. A status table that misreports its own status is
worse than no table, for the reason `QueryGate` exists: it reads as working.

## 2. Architectural principles — 2 built, 1 partial, 1 absent

| # | Requirement | Status | Where it stands |
|---|---|---|---|
| 2.1 | Fully microservices-based | **Not started** | One Express + tRPC app, one Postgres, one Vercel function. The seams are clean — each `Backend/` module has 1–4 relative imports and **no cross-module transactions** — so splitting later is packaging, not a rewrite. See the note at the foot of this file. |
| 2.2 | Easy for all five parties | **Built** | All five now have a real interface, and the fifth was the whole of this gap. The buyer has the storefront; the vendor and the admin share `/admin`, scoped by the server; the person who processes orders has `/admin/orders`, where a line is moved from pending to delivered and a driver's cash is recorded; and the delivery company has `/admin/dispatch` — see 3.4.1. What is still thin is named under 3.4 and is not a missing audience: there is no map and no live ETA. A courier can see every parcel assigned to them, what it takes to carry, where it goes and how much cash to collect, and can mark it collected and handed over. |
| 2.3 | Every advanced feature optional | **Built** | `/admin/features` is the switchboard — twenty switches, admin-only (`platform.configure`), every change on the audit trail with the authorisation chain. `Shared/features.ts` is the list and is pure, imported by both sides, so the page hides exactly what the API refuses. **A switch closes the door; it never locks anybody in the room**: off refuses *starting* something — a return, a price request, a claim, a gift card — and leaves everything already in motion to finish, so an open return is still refunded and an agreed price still honoured. The refusal is one middleware on the base procedure, by path, the shape `refuseNul` already has, so no router can forget it; a test fails if a switch names a procedure the API does not have. Rails answer empty rather than refuse. **`ai` is the one switch over every model call** — assistant, search refinement, recommendation ordering, the review queue's model pass — each landing on the deterministic fallback it already had for "no key". Absent is on: a database nobody has touched behaves exactly as before. What is still per-vendor rather than per-shop is unchanged and already existed: `autoPublish`, cash on delivery, accepting price requests. |
| 2.4 | AI core, not an afterthought | **Partial** | AI now runs through the shopper's side and the operator's: the recommendation rail and its model reorder pass (3.1.5), search refinement, a shop assistant on every shopping page and the product assistant on every product page (both through the Gemini gateway, which suggests NetLet searches rather than naming products), a listing drafter on the new-product form that a seller reads before anything is filled in, auto-categorisation on bulk upload (3.3.5), the review queue's triage with a model pass that can only add a concern (3.3.6), fraud signals on orders (3.6.5), photo search, which turns a picture into a few search words (3.1.6), and drafted support replies a person edits and sends (3.5.1). Every one of them is Gemini, through one Cloudflare gateway that holds the only key. Every one carries the same guardrails — a model reorders or flags but never chooses or refuses, no shopper's identity leaves NetLet, merchant text is fenced as data, and every failure lands on a deterministic answer — and one switch (`ai`, 2.3) turns every model call off at once. **Pictures are drawn now too**, through the same gateway's image model: a seller's photo cleaned up onto white beside the rule-fixed one (3.3.4), a shopper trying clothes on from their own photo (3.1.8, off until switched on), a step's picture in a guide (3.5.3) — and the maker's page is found by a search-grounded call rather than typed (3.1.10). Each is counted per account before the call, and what comes back is a picture by its own bytes or a refusal, prepared in the browser and stored only when a person chooses it. Still absent, and why this stays partial: the WhatsApp and voice legs of the contact centre (3.5.1, whose chat answers from facts rather than a model) and the language-model half of anything a shopper asks a person today. The size guide (3.1.20) learns from returns instead. Those wait on providers rather than code. |

## The one recommendation I would put in front of the plan

**Stay a modular monolith until payments and fulfilment are real, then split.**

The goal in 2.1 is that a new feature ships without disturbing the rest of the
system. That goal is met today by the module boundaries, not by the network:
`Shared/` is pure and holds every rule that costs money or access, guards sit
next to the queries they protect, and no transaction spans two modules. Those
are the properties that make a split cheap — and they are exactly the
properties a premature split destroys, because once `orders` and `inventory`
are two services, taking stock during checkout stops being a transaction and
becomes a saga with compensating writes.

The cost of waiting is low: the seams are measured above and they hold. The
cost of splitting now is paid on every feature in this document, before a
single dinar has been taken.

If the answer is still "split now", say so and I will — the document wins over
my recommendation. But I would want the payment and delivery services carved
out **first**, since those are the two with genuinely independent failure
modes and genuinely different scaling, and the rest to follow only when
something forces it.
